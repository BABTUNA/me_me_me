[Bartie](/blog/bartie-postgres-cdc) is a small Postgres CDC engine I built to understand how systems like [Artie](https://artie.com) work, and it was something you ran from a terminal. **[Super Bartie](https://github.com/BABTUNA/SuperBartie)** is the same engine, unchanged, running as a service: an API that reports what the pipeline is doing, a second destination that turns each change into a vector, an MCP server so an agent can operate it, and a deployment with a page in front.

## Try it

**[Open the live console](/super-bartie/live)** to watch rows land, move a sighting on the source and see it arrive, and ask the same question of a live copy and a stale one. You can also [browse both databases side by side](/super-bartie/data).

## Where the lag is

Most pipelines tell you how far behind they are. The [control API](https://github.com/BABTUNA/SuperBartie/blob/main/docs/phase-6-control-api.md) also says where, with three numbers next to the usual per-table latency:

- **Reader lag**: the source WAL ahead of what the reader has acknowledged.
- **Backlog**: messages the broker holds that the writer has not committed.
- **Merge time**: how long the writer's `MERGE` transactions take.

Whichever one grows names the bottleneck: the reader, the writer, or the destination.

## A second destination

A model reading a nightly copy of your data will confidently tell you yesterday. To show it, a [second consumer](https://github.com/BABTUNA/SuperBartie/blob/main/docs/phase-7-vector-destination.md) reads the same Redpanda topic, turns each changed row into a sentence, embeds it, and upserts it into pgvector. It commits offsets only after the vector transaction commits, the same rule the writer follows.

The console asks one question of two copies: the live vector table, a couple of seconds behind the source, and a snapshot of it refreshed every five minutes. Move a sighting, ask again, and they disagree.

## An agent interface from the contract

Artie's MCP server generates its tools from an API contract. Super Bartie's [MCP server](https://github.com/BABTUNA/SuperBartie/blob/main/docs/phase-8-mcp.md) does the same from one OpenAPI file, with Artie's tool names wherever an equivalent exists. Two tools have none: `pipeline_verify` checksums every table on both databases, and `destination_ask` queries the vector copy. Ask Claude Code "why is my pipeline slow?" and it names a component, not just a number.

## One box

Everything runs in Docker Compose on a single VM behind Caddy: source Postgres, Redpanda, destination Postgres with pgvector, and the four Go binaries from one image. A nightly job drops every volume and brings the stack back up, which wipes the demo data and also exercises the fresh-slot backfill path every night.

## Where it stops

One pipeline, one tenant, one bearer token. No schema evolution, the same limit as Bartie. The vector destination embeds two tables and does not rewrite a document when a row it was enriched from changes. The MCP server is local over stdio, with no hosted endpoint.
