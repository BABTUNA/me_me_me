[Super Bartie](https://github.com/BABTUNA/SuperBartie) is a follow-up to [Bartie](/blog/bartie-postgres-cdc), the small Postgres CDC engine I built to understand how [Artie](https://artie.com) works. Bartie ran from a terminal. For this version I left the reader and writer alone and built the parts around them: an API for checking on the pipeline, a second destination that stores vectors, an MCP server, and a deployment I can link to.

## Try it

The pipeline is running at **[/super-bartie/live](/super-bartie/live)**. You can watch rows get replicated, change a row yourself, and ask questions about the data. There is also a [page that shows both databases](/super-bartie/data) next to each other.

## What I added

### 1. An API that shows where the lag is

With Bartie, the only way to see what was happening was to read logs. I added an [HTTP API](https://github.com/BABTUNA/SuperBartie/blob/main/docs/phase-6-control-api.md) that reports status, errors, and latency. Latency alone did not tell me which part was slow, so it also returns three more numbers:

| Number | What it measures | If it grows |
| --- | --- | --- |
| Reader lag | How far the source WAL is ahead of the reader | The reader or the source is slow |
| Backlog | Messages in Redpanda the writer has not applied yet | The writer is behind |
| Merge time | How long each `MERGE` takes on the destination | The destination is slow |

I copied the URL layout from Artie's public API. Their usage endpoint returns latency per table, and mine adds these three fields.

### 2. A second destination for vectors

Artie has [written about](https://www.artie.com/blogs/ai-data-integration) why AI systems need fresh data, and I wanted to see it for myself. I added a [second consumer](https://github.com/BABTUNA/SuperBartie/blob/main/docs/phase-7-vector-destination.md) that reads the same Redpanda topic as the writer. For each changed row it builds a sentence, embeds it, and stores it in pgvector.

The demo keeps two copies: the live table, which is about two seconds behind the source, and a snapshot that refreshes every five minutes. If you change a row and ask the same question against both, only the live copy has the new answer.

### 3. An MCP server

Artie recently shipped an [MCP server](https://github.com/artie-labs/artie-mcp). Reading the repo, I saw that it generates its tools from an OpenAPI spec instead of defining them by hand. I did [the same](https://github.com/BABTUNA/SuperBartie/blob/main/docs/phase-8-mcp.md) with a spec for my API and used their tool names where the endpoints matched.

I also added two tools they do not have. `pipeline_verify` compares checksums of every table in both databases, and `destination_ask` searches the vector table.

## Running it

Everything runs with Docker Compose on one VM: the source Postgres, Redpanda, the destination Postgres with pgvector, and the Go binaries. Caddy handles TLS. A cron job resets the data every night, which also means the backfill runs from scratch once a day.

## What is missing

It runs one pipeline and has one API token. It still does not handle schema changes, same as Bartie. The vector table only covers two of the source tables. The MCP server only runs locally.

The code is on GitHub: **[Super Bartie](https://github.com/BABTUNA/SuperBartie)**, and the engine it is built on, **[Bartie](https://github.com/BABTUNA/Bartie)**.
