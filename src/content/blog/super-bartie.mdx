[Bartie](/blog/bartie-postgres-cdc) is a small Postgres CDC engine I built to understand how systems like [Artie](https://artie.com) work. It was something you ran from a terminal: two Go processes, a few scripts, a video.

**[Super Bartie](https://github.com/BABTUNA/SuperBartie)** is the same engine running as a service. The reader and the writer did not change. What changed is everything around them: an API that reports what the pipeline is doing, a second destination that turns each change into a vector, an MCP server so an agent can operate it, and a deployment with a page in front.

## Where the lag is

Most pipelines can tell you how far behind they are. I wanted Bartie to say where.

The [control API](https://github.com/BABTUNA/SuperBartie/blob/main/docs/phase-6-control-api.md) reports three numbers next to the usual per-table latency:

- **Reader lag**: how far the source WAL is ahead of the position the reader has acknowledged.
- **Backlog**: messages the broker holds that the writer has not committed.
- **Merge time**: how long the writer's staging and `MERGE` transactions take.

Whichever one grows names the bottleneck. Reader lag growing with a flat backlog is the reader or the source. Backlog growing with flat merge times is the writer. Backlog and merge time rising together is the destination. Pause the writer and you can watch the backlog climb while reader lag stays flat, then drain when it resumes.

The paths and response shape follow Artie's public API where one exists, with these fields added. Each process serves its own small metrics endpoint and appends errors to a shared file, so the API never shares a connection pool with the pipeline.

## A second destination

Artie's argument for real-time data in AI systems is that a model reading a nightly copy will confidently tell you yesterday. I wanted to see that argument run.

A [second consumer](https://github.com/BABTUNA/SuperBartie/blob/main/docs/phase-7-vector-destination.md) reads the same Redpanda topic under its own consumer group, renders each changed animal or observation as a sentence, embeds it, and upserts it into pgvector. It follows the writer's rule: offsets commit only after the vector transaction commits. Embedding happens before the transaction, so a crash in between re-embeds on replay.

The console asks one question of two copies. The live copy is the vector table, a couple of seconds behind the source. The batch copy is a snapshot of that table refreshed every five minutes, which is generous to batch. Edit the demo row, ask again, and they disagree.

Two details mattered. An update that leaves a TOASTed `notes` column untouched arrives without the text, so there is nothing to re-embed and the row is skipped. And the default embedder is a deterministic keyword hash, so the whole stack runs with no API keys; a real embedding model is one environment variable.

## An agent interface from the contract

Artie's MCP server does not hand-write its tools. It generates them from an API contract and ships skills that tell an agent how to sequence the calls. Super Bartie's [MCP server](https://github.com/BABTUNA/SuperBartie/blob/main/docs/phase-8-mcp.md) is built the same way: one OpenAPI file, tools generated from it, and the operation names are Artie MCP's tool names wherever an equivalent exists.

Two tools have no equivalent. `pipeline_verify` checksums every table on both databases, which needs destination access. `destination_ask` queries the vector copy. The monitoring skill carries the triage table above, so asking Claude Code "why is my pipeline slow?" gets a component, not just a number.

A small test keeps the skills honest in both directions: every tool a skill names must exist in the contract, and every tool in the contract must be mentioned by a skill.

## One box

Everything runs in Docker Compose on a single VM behind Caddy: source Postgres, Redpanda, destination Postgres with pgvector, and the four Go binaries from one image. A nightly job drops every volume and brings the stack back up, which wipes the demo data and also exercises the fresh-slot backfill path every night.

## What I learned running it

- **Verify needs a quiet moment.** With a write every two seconds and a two-second flush, a row is almost always in flight. A single checksum pass can mismatch on a healthy pipeline, so verify retries until it converges or a deadline passes.
- **A hard kill leaves no log line.** The error log shows what a process recorded before failing. After `kill -9` the evidence is the process being unreachable, not an entry.
- **The reader recovers from a dropped replication connection by exiting.** The container restarts, the slot still holds the position, and streaming resumes. My laptop sleeping produced this several times a day, and the copy still verified.

## Where it stops

One pipeline, one tenant, one bearer token. No schema evolution, the same limit as Bartie. The vector destination embeds two tables and does not rewrite a document when a row it was enriched from changes. The MCP server is local over stdio, with no hosted endpoint.
